## 〇 先说结论

1. **名字**：Doctor Duck，口号沿用 "Trust me, I'm a Ducktor."。logo 的三个方向见第五节。
2. **拆黑盒能做，但不能靠 AI 自述。** 三篇论文和 Anthropic 的一项可解释性研究都说明，模型自己讲出来的思路，常常和它实际的做法对不上。所以 `/duck-why` 从产物和过程记录里重建思路，对照标准做法，再给你一个自己核对的办法。过程记录里最可靠的，是能对账的事实：试了什么、测出多少、谁拍的板。（第一节）
3. **写作指导**：哈佛和 MIT 各找到 4 份可用的教程，其中 MIT 有 2 份可以改编收录。名家意见不一致的地方，两派都摆出来。（第一节）
4. **和 Ponytail 的关系**：壳像它，肚子像 Superpowers，记性像 Compound Engineering。（第二节）
5. **命令**：你提的 `/duck-refine-paper` 这种"前缀加短横"的写法，正是成熟项目改了几轮名以后收敛到的。另一种是直接用插件自带的命名空间（`/duck:review`），在 Codex 里更短，但离开插件安装就容易撞名。我建议走前一种，再收紧三处：子命令只用一个词（`/duck-review`），缩写由你自己定义，`/duck` 本身当总入口。（第三节）
6. **热插拔**：插件本体只读。你加的、改的技能和设定都放在项目里，两个宿主都不用重启。改内置技能时先复制一份再改，随时能还原。（第四节）

## 一 拆黑盒：把 AI 做事背后的思路讲给你

### 1.1 先绕开一个坑：AI 讲不清自己"当时怎么想的"

你想让它拆出 Agent 内部用到的思想。这里有个坑：模型自己讲出来的思路，不管是边做边写的推理，还是事后的解释，都不一定是它实际用的思路。三篇论文都测到了这一点：

- **Turpin 等，2023**：在少样本示例里把正确答案都排在 (A)，模型就会偏向选 (A)。可它写出来的推理几乎从不提这一点，反倒会给错误答案编出一套像样的理由。在 BIG-Bench Hard 的 13 个任务上，准确率最多掉了 36%。（arXiv 2305.04388）
- **Lanham 等，2023，Anthropic**：模型对自己写下的推理依赖多少，任务之间差别很大，有时几乎不看。模型越大，多数任务上的推理反而越不忠实。（arXiv 2307.13702）
- **Chen 等，2025，Anthropic**：推理模型用了提示里给的线索，但在推理过程里承认用过的比例常常低于 20%。（arXiv 2505.05410）

Anthropic 2025 年的可解释性研究里还有个直观的例子。问 Claude 3.5 Haiku 怎么算出 36+59=95，它回答说用的是竖式进位。可从模型内部看，它走的是两条并行的路：一条估个大概，一条专门算准个位。（"Tracing the thoughts of a large language model"，2025-03-27）

所以 `/duck-why` 不承诺"回放 AI 的内心"，只承诺四件能核对的事：

1. **认产物**：看代码、公式、段落本身，认出用的是哪种标准思路，比如"这是块稀疏"或"这是贪心加交换论证"。这一条对着产物就能核对，不靠 AI 自述。
2. **还原过程**：从过程记录里还原决策链：读了什么、试了什么、哪一步改了主意、哪些是你定的。
3. **对照**：这类问题的标准做法和替代方案各是什么，这次为什么选了这个。
4. **给你核对的办法**：一个小实验、一个反例或一个估算，你想确认上面讲的对不对，可以自己试。

每份报告都带一句："以上根据代码和过程记录重建，不是 AI 内部过程的回放。"

**能对账的事实最可靠。** 过程记录里，试过什么、测出多少、改了哪几行、哪一步是你拍的板，这些都能对账。决策行里写的"为什么"仍是 AI 自己说的，报告会拿它和事实对一遍，对不上就标出来。决策行写在结果出来之前，至少不会被结果带偏。所以讨论稿里常驻的"决策行"要留着：做事当下写一行"选了什么、放弃了什么、谁定的"。`/duck-why` 先读这些记录，再看产物。

`/duck-why` 能拆的对象：刚才那一步（默认）、一个文件或函数（`/duck-why src/skip_attn.py`）、一次提交（`/duck-why HEAD~2`）、一段文字（`/duck-why 引言第三段`）。这件事是不是插件技能做的都行，Claude Code 或 Codex 自己写的代码也能拆。MVP 先读当前会话和 git 记录。两个宿主都在本地存会话记录，读以前的会话放第二步。

### 1.2 示意：拆一个算法

接着上一份示意稿里小周的故事。AI 替小周实现了"跳过部分注意力计算"：

```
小周：/duck-why 刚才那版实现，为什么按 64 个 token 一块来跳，不一个一个跳？

鸭子：── 拆一下 ──────────────────────────────
  用的思路：块稀疏。每 64 个 token 一块，整块要么算、要么跳。
  为什么：GPU 算注意力是一块一块读写显存的。一个一个跳，读写变零碎，
    省下的计算被访存吃掉，时间几乎不降；整块跳，这块的读写直接省掉。
    FlashAttention 论文开头点的就是这个问题：很多近似注意力降了计算量，
    墙钟时间却没降，缺的是把显存读写算进去。（Dao 等，2022）
  这次的过程：第 3 步先写了逐 token 跳，测得只省 4% 的时间；第 4 步
    改成 64 一块，省了 31%。这一步是 AI 定的，你当时没参与。
  放弃了什么：逐 token 跳得更细，准确率可能掉得更少，但测不出加速。
  （以上根据代码和过程记录重建，不是 AI 内部过程的回放。）

  你能带走的一条：理论计算量降了，不等于时间降了。做加速先问省下的是
    计算还是显存读写，再按硬件的块大小设计稀疏。
  要核对的话：把块大小换成 16、32、128 各跑一次，看加速比在哪儿拐弯。
```

最后两段会记进笔记本，下次做加速相关的事，它会翻出来接着讲。

### 1.3 写作指导：引哈佛、MIT 这些名家

名家教程做成一个**经验卡片库**。每张卡片写四样东西：
- 一条原则，用我们自己的话转述；
- 出处：作者、机构、年份、链接；
- 能用到什么程度：可以改编收录、只能短引，或者只能放链接加转述；
- 适用哪个阶段、哪个技能。

写作类任务的「为什么」，从这里取依据。哈佛和 MIT 的来源，今天核实了这些：

| 来源 | 机构 | 讲什么（节选） | 能用到什么程度 |
|---|---|---|---|
| CommKit 论文系列页 | MIT EECS Communication Lab | 动笔前先定受众和目的；摘要按六步写；从贡献倒推引言的故事 | 可以改编收录（CC BY-NC 4.0） |
| 21W.794 研究生技术写作课 | MIT OCW，2019 | 把论文当一种文体来读；写完用反向提纲（把每段的要点抽出来连成一串）检查每段是否服务于主张 | 可以改编收录（CC BY-NC-SA 4.0） |
| Freeman《How to write a good CVPR submission》 | MIT CSAIL | 引言开门见山，尽早讲清贡献 | 短引加转述 |
| Durand 的写作与 rebuttal 笔记 | MIT CSAIL | rebuttal 先回应重要且能赢的点，不复述批评 | 短引加转述 |
| Whitesides《Writing a Paper》 | Harvard 化学系，2004 | 先用数据（图、表）搭提纲，和导师过四五轮再写正文；按重要性排，不按时间排 | 短引加转述 |
| Weitz 组写作指南 | Harvard SEAS，2012 | 先写出一句话结论；先选好图和图注，再写正文 | 短引加转述 |
| Pinker《Why Academics Stink at Writing》 | Harvard 心理系，2014 | "知识的诅咒"是写不清楚的一大原因；少用元话语，少用条件反射式的保留语 | 短引加转述 |
| 《A Student's Guide to Writing in the Life Sciences》 | Harvard MCB 与 Harvard Writing Project，2007 | 论文是用数据搭起来的论证 | 短引加转述 |

另有 Stanford、Berkeley、CMU 等 40 多条，10-15 已经核实过，比如 Widom 的引言五问、Gopen & Swan 讲的句子里新旧信息的顺序。哈佛没找到计算机系教授写的指南，上面几份来自化学、物理、心理和生命科学。

现有 11 个技能的写作部分，讲的是"怎么做"，出处基本是手册本身。我查过 paper-writer、intro-drafter、paper-polish 等技能的文件，几乎没有外部链接。所以名家这一层是新加的，正好补上"为什么"。

名家意见不一致的地方，两派都摆出来，再按你这篇的情况给建议。两次调研一共找到近十处这样的分歧。下面的示意用的正好是哈佛和 MIT 的一处：

```
小周：/duck-why 你为什么让我最后再写引言？

鸭子：这一处名家分两派，都摆给你：
  · 先写：Weitz（Harvard）让学生先起草引言，全文写完再重写一遍；
    引言要一路引到那个"唯一的关键未知"，也就是你的结论。
  · 后写：MIT 的 CommKit 建议引言放到最后写，从贡献倒推故事。
  我让你最后写，是因为你的实验还在变，贡献还没定，先写的引言多半要
    推倒重来。你要是习惯 Weitz 的做法，也可以现在先起一版当路标，
    第 6 周结果稳了，再按 CommKit 的办法从贡献倒推重写。
  你能带走的一条：引言围着贡献转。贡献没定，引言写得再好也是草稿。
  出处卡片和原文链接存在 .duck/reports/ 里。
```

### 1.4 现成的有没有

最接近的是 Claude Code 自带的两种输出风格：
- Explanatory：在回复里插 Insight 框，讲实现上的选择。
- Learning：在 Explanatory 的基础上，还会在代码里留 `TODO(human)`，让你亲手写几行。

鸭子比它们多四样：
- 讲研究，不只讲代码；
- 依据带出处，来自手册和名家；
- 经验记进笔记本，下次接着用；
- Codex 里也能用。

## 二 Ponytail 现在什么样，我们像不像它

### 2.1 Ponytail 现在的样子

10-15 拆过一遍，今天补了最新数据。

- **一句话**："让 agent 像屋里最懒的资深工程师"：只写最少的代码，但校验、安全、无障碍一样不砍。
- **规模**：今天 164,987 星，MIT 许可。最新版 v5.3.1，今天刚发布。
- **结构**：核心是一页 52 行的 prompt（`skills/ponytail/SKILL.md`），外加 5 个小技能。其余约 2,400 行是 hook（宿主在固定时刻自动跑的小脚本，比如会话开始时）、适配器和脚本，作用是把同一份 prompt 送进约 30 个宿主。
- **用起来**：装好后每个会话自动生效，你照常提需求。区别在两处：
  - 它写得少。README 里的例子是日期选择器，从 335 行变成 10 行。
  - 每条回复末尾有 1–2 行，交代跳过了什么、没查什么、有什么风险。
- **命令**：
  - `/ponytail lite|full|ultra|off`：切档。
  - `/ponytail-review`：审改动。
  - `/ponytail-audit`：审全仓。
  - `/ponytail-debt`：把欠下的捷径汇成账本。
  - `/ponytail-gain`：看基准成绩。
  - `/ponytail-help`：查命令。
  - `/ponytail band`：开关 5.3 新加的状态栏（见下）。
- **5.3 的新东西**：Claude Code 输入框上方多了一条状态栏，显示当前任务花了多少钱、多少 token、多少 agent 时间，复用已有代码的比例，以及最后一次改动后测试过没过。另有一个本地网页，汇总所有项目的这些数字。数据只存在本机。
- **效果**：作者自测，代码少 53%、成本少 26%。JetBrains 用 80 对任务复测：代码少 15.4%（p=0.088，不显著），成本少 10.3%（p=0.004）。首版宣称的 80–94% 被指出基线太啰嗦，作者两天内重做基准并认了错。
- **最要紧的一条证据**：JetBrains 测过只装技能、不装 hook 的情况，10 次会话里自动触发 0 次。所以常驻注入是刚需。

### 2.2 对照

| | Ponytail | Doctor Duck |
|---|---|---|
| 人设 | 最懒的资深工程师 | 小黄鸭导师：平时你对鸭子讲代码，这回鸭子给你讲 why |
| 方向 | 让 agent 少写 | 让你多懂，关键处你来定 |
| 常驻部分 | 一页 prompt，由 hook 在会话开始时注入 | 一页导师规则（先问、决策行、「为什么」报告的格式），同样由 hook 注入 |
| 每轮交代 | 末尾 1–2 行：跳过了什么、有什么风险 | 末尾一行决策：选了什么、放弃了什么、谁定的 |
| 按需技能 | 5 个，都很小 | 11 个继承来的大技能，加 why、learn、技能管理 |
| 账本 | `/ponytail-debt` 汇总欠下的捷径 | `.duck/notebook.md` 汇总经验 |
| 档位 | lite / full / ultra / off | on / quiet / off，另外可以按类静音 |
| 新技能 | 只由作者加 | 本地随便加、随便改；想分享就提 PR，署你的名 |

一句话：**壳像 Ponytail，肚子像 Superpowers，记性像 Compound Engineering。**
- 壳：人设、常驻注入、每轮交代、档位、账本，都照 Ponytail 来。
- 肚子：Superpowers 在会话开始时注入一个引导技能，由它带一堆按需技能。我们是一页常驻规则，带十几个子命令。
- 记性：Compound Engineering 做完一件事后敲 `/ce-compound`，把经验写进项目的 `docs/solutions/`，之后 `/ce-plan` 做规划时会读。我们的笔记本是同一个思路，只是记的是研究原则。

### 2.3 表里没写的三条

- **拿：改规则前先过评测。** Ponytail 要求每次改规则都附三组对比：基线、现版、改动，每组至少跑 6 次。
- **不拿：品牌标记。** Ponytail 早期往代码里写 `ponytail:` 注释，有人因此卸载（issue #120）。所以鸭子的报告和决策行只出现在对话和 `.duck/` 里，不进论文，也不进代码。
- **先不学：5.3 的状态栏。** 它统计的是 agent 的花费，本身没问题；可换到我们这里，很容易做成给你打分的面板，这正是 7 月否掉的东西。

## 三 命令怎么设计

### 3.1 四种写法，成熟项目怎么选的

| 写法 | 谁在用 | 结果 |
|---|---|---|
| 前缀加短横：`/duck-review` | Ponytail（`/ponytail-review`）、caveman（`/caveman-commit`）、Spec Kit（`/speckit-plan`）、Compound Engineering（`/ce-plan`）、BMAD（`/bmad-build`） | 最常见。Spec Kit 和 Compound Engineering 都是改了几轮名，最后落到这一种 |
| 命名空间加冒号：`/duck:review` | 插件自带这一层：插件叫 duck、技能叫 review，Claude Code 里就是 `/duck:review`，Codex 里是 `$duck:review`。SuperClaude（`/sc:implement`）和 OpenSpec（`/opsx:apply`）是自己建子目录做出来的 | Codex 里最短。但离开插件安装（复制到别的宿主、用 skills 工具装），名字就只剩 `review`，和别人撞；冒号写法在 VS Code 里不工作（Spec Kit #913）。OpenSpec 有个提议，要在多数工具里改成 `/openspec-propose` |
| 一个入口加参数：`/duck review` | Ponytail 切档（`/ponytail ultra`）；BMAD 的 `/bmad` 后面接一句话 | 多用来切档。caveman 原来用 `/caveman lite\|full\|ultra` 切档，v3.1 拆成三个独立命令，旧写法只留作别名 |
| 缩写：`/duck-rp` | 少见：OpenSpec 的 `/opsx:ff`，BMAD 的 agent 菜单里两个字母的代码 | 命令行设计指南 clig.dev 反对随意缩写；别名可以有，但要写明、不变 |

两条反面教训：
- **不带前缀会撞名。** Claude Code 自带 `/review` 和 `/code-review`，agent-skills 的 `/review` 因此只能写成 `/agent-skills:review`。gstack 默认用不带前缀的短名，到了 Copilot 上 `/review` 撞了内置命令，只好改叫 `/gstack-review`。Compound Engineering 改名时给的理由是：setup、plan、review 这种通用名，装几个插件就撞了。
- **靠关键词自动触发容易误伤。** oh-my-claudecode 曾经在普通句子里认关键词，"plan this" 误触发太多，后来删了（#824）。

### 3.2 我的建议：走前缀加短横，再收紧三处

你提的 `/duck-refine-paper` 就是第一种写法。前两种我仔细比过，差别主要在 Codex 和别的宿主上：

| | `/duck-review`（前缀加短横） | `/duck:review`（插件命名空间） |
|---|---|---|
| Claude Code | `/duck-review`，不撞名；全名 `/duck:duck-review` 也能用 | 只能敲 `/duck:review`，因为 `/review` 是内置命令 |
| Codex（装成插件） | `$duck:duck-review`，多打 5 个字 | `$duck:review` |
| 别的宿主、用 skills 工具装 | 还是 `duck-review`，不撞 | 只剩 `review`，和别人撞 |

你最早的要求是轻量、好适配，所以我选前缀加短横：在 Codex 里多打 5 个字，换来在哪个宿主都不撞名。Ponytail 在 Codex 里也是这么写的：`$ponytail:ponytail-review`。

在这个基础上收紧三处：

1. **子命令只用一个词**：`/duck-review`、`/duck-polish`、`/duck-why`。插件里全是论文和研究的事，`-paper` 可以省掉。名字够短，就用不着缩写。Claude Code 的命令菜单还会从名字里的任一个词开始匹配，敲 `/polish` 就能找到 `/duck-polish`。
2. **缩写由你自己定义**：`rp` 可以是 refine paper，也可以是 review paper 或 related papers；内置一个缩写，以后加命令都得绕着它走。clig.dev 的意思是：别名没问题，省打字是好事，但要写明、不变。所以不内置，要用就自己加：`/duck-skill alias rp refine` 会在项目里生成一个 `/duck-rp`，效果和 `/duck-refine` 一样。它是一个普通子命令，照样能强行指定。
3. **`/duck` 本身当总入口**，只管三件事：
   - 不带参数：鸭子 quack 一声，列出全部子命令，包括你自己加的；
   - `/duck on`、`/duck quiet`、`/duck off`：开关报告（第四节）；
   - 其余都当一句话处理：`/duck 帮我看看这段`，替你挑一个子命令，先说一句按哪条处理，再读那条命令的包装文件照做。子命令设了 disable-model-invocation，只有你敲才会触发，AI 不能自己调用，所以总入口是直接读包装文件（10-17 补，见《项目架构》§四）。

   clig.dev 还反对"兜底子命令"，怕以后加新词，旧写法的意思就变了。这里风险小：新子命令都做成独立的 `/duck-xxx`，`/duck` 后面保留的词只有 on、quiet、off，固定下来不再加。

**三种叫法，确定性从高到低：**
- 敲 `/duck-review`：一定走审稿，不经过任何猜测。
- 敲 `/duck 帮我看看这段`：鸭子自己选，先说一句"按润色处理；要审稿请敲 /duck-review"，再动手。路由本身也不是黑盒。
- 不敲斜杠，只说"帮我看看这段"：MVP 里鸭子只提议、不自动跑，比如"这件事 /duck-polish 能做，要按它来吗？"。自动跑放第二步，先测误触发率。上一份示意稿里写的"不敲斜杠也会触发"，改成先提议。

**子命令的描述不占上下文。** 11 个继承技能的描述加起来 5,300 多个字符。Claude Code 给所有技能描述的总预算只有上下文窗口的 1%，你装的其他插件也要分这一份。所以子命令都设成只能手动调用（`disable-model-invocation: true`），描述就不进上下文。`/duck` 选好子命令以后，直接读它的说明文件照着做。Codex 有没有一样的开关，搭骨架时实测。

## 四 热插拔、自定义、改插件自己

### 4.1 原则：插件本体只读，你的东西都放项目里

Claude Code 的文档写明，插件目录升级时会换掉，不要往里写东西。所以内置技能随插件安装和升级，不在原地改；你加的、改的、设定的，都放在项目里：

```
.duck/
  config.md       你的设定：报告开关、按类静音、关掉的子命令（10-17 改：组里的规矩挪到 cards/）
  notebook.md     笔记本
  reports/        完整的「为什么」报告
  decisions.md    决策行，AI 写决策行时顺手追加进来（10-17 改，不再靠每轮结束时的 hook 抄）；只按时间记，不汇总、不算比例
  skills/         你改过的内置技能和核心规则（副本）
  cards/          你和你们组的卡，带自己的 INDEX.md（10-17 新增）
.claude/skills/duck-xxx/   你新建的技能和别名，Claude Code 从这里读
.agents/skills/duck-xxx/   同一份，给 Codex
```

`config.md` 是给人看的普通文档，你可以直接改，也可以让鸭子改。组里的规矩，比如"图一律用色盲友好配色""正文里不用 utilize"，10-17 改为写成卡片放进 `.duck/cards/`，每条 `/duck-*` 命令开头都先读（见《项目架构》§一②）。

### 4.2 热插拔：两个宿主都不用重启

- Claude Code：`.claude/skills/` 里新增或改动的技能当场生效，文档原话是 "without a restart"。插件自带的技能，要敲 `/reload-plugins` 或开新会话。
- Codex：项目的 `.agents/skills/` 有改动会自动发现，文档原话是 "Codex detects skill changes automatically"。

所以你加的技能放在项目目录里，两边都能热插拔。两个宿主读的目录不一样，鸭子写一份，另一边放一个链接。Codex 认不认链接，搭骨架时实测，不认就写两份。有一个例外：项目里原来没有 `.claude/skills/` 这个目录时，第一次新建技能后要在 Claude Code 里敲一次 `/reload-skills`。

### 4.3 `/duck-skill`：加、减、改

| 你敲 | 做什么 |
|---|---|
| `/duck-skill list` | 列出全部技能：内置的、你加的、你改过的，各自开没开 |
| `/duck-skill disable figure`，`/duck-skill enable figure` | 关掉或打开一个子命令，记在 `config.md` 里。Claude Code 没法单独关掉插件里的某个技能（文档说 skillOverrides 管不到插件技能），所以由鸭子自己查，见表下 |
| `/duck-skill new rebuttal` | 新建技能：把刚才那套做法，或者你的一段描述，写成 `/duck-rebuttal`。写好先拿一个真实任务试跑，你看过结果再定稿 |
| `/duck-skill edit review` | 改内置技能：先把原版复制到 `.duck/skills/`，只改副本，并给你看和原版的差异 |
| `/duck-skill reset review` | 删掉副本，回到原版 |
| `/duck-skill card new`，`card edit`，`card off` | 加、改、静音经验卡片：写进 `.duck/cards/`，并更新那里的 INDEX.md；直接说「记成我们组的规矩」也行。写之前都先给你看（10-16 新加，见《名校教程和技能的关系》） |
| `/duck-skill alias rp refine` | 生成 `/duck-rp`，等于 `/duck-refine`（见第三节） |
| `/duck-skill share rebuttal`（第二步） | 整理成 PR 提给 Doctor Duck 仓库，署你的名。改自继承技能的，保留原技能的署名和许可：文件头标了的照标（6 个是 CC BY 4.0，4 个是 CC BY-NC-SA 4.0） |

**每个子命令先查两件事。** 内置子命令的第一步都是看一眼 `.duck/`：被关掉了，就回一句"已关闭，敲 `/duck-skill enable figure` 可以打开"，然后停下；有你的副本，就照副本做。直接敲、经 `/duck` 路由、在 Codex 里敲 `$duck:duck-review`，走的都是这同一套检查，不靠宿主自己的同名规则。

"改插件本身"也走这条路。比如你说"以后决策行别写这么长"，鸭子先判断这是设定还是规则：是设定，就改 `config.md`；是规则，就改核心规则的副本。两种都先给你看改动，你同意了才写。

### 4.4 防翻车

- 每次改动先给你看差异，你点头才写。官方的 claude-md-management 插件也是这条规矩："Only edit files they approve"。
- 改动全在项目里的普通文件上，可以进 git，随时回退；`reset` 一步回到原版。
- 新技能先试跑、再定稿。官方的 skill-creator 先给旧版存快照，把结果给你看，再按你的意见改；Superpowers 的 writing-skills 更严，要求先有一个失败的测试，才能写技能。
- 想把改动提回上游时，学 Ponytail 的规矩：改核心规则要附对比评测。只在本地自己用的，不设门槛。

### 4.5 报告的开关

你说的"文档可以开关"，具体是三档，再加一个按类静音：
- `/duck on`（默认）：每次实质性任务后出报告，对话里显示短版，完整版存进 `.duck/reports/`。
- `/duck quiet`：照记照存，对话里不显示。
- `/duck off`：鸭子整个歇着，常驻规则不再注入；子命令照样能手动叫。
- 按类静音：说一句"这类我懂了"，这一类以后只记不讲。这条记在 `config.md` 里，删掉那一行就恢复。
