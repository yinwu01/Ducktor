## 〇 先说结论

1. **会改进技能。** 名校教程通过四条路起效：

## 一 教程怎么起效：四条路

| 路 | 什么时候起作用 | 改了什么 | 能不能定轻重 | 例子 | 什么时候做 |
|---|---|---|---|---|---|
| ① 加查项 | 以后每次跑这条命令 | 包装文件里钉几张卡，原技能正文不动 | 能，因为评测过 | `/duck-review` 加查「主结果有没有报多次运行的波动」 | MVP 最后一步做第一条，之后逐条加 |
| ② 当尺子 | 每次跑 `/duck-*` | 开头读你们组的卡；收尾挑至多三张共识卡 | 你们组的卡按卡上写的定；共识卡只提醒 | 你们组有张卡写「表里每个数写明种子数」，`/duck-write` 写表时照做，`/duck-review` 审稿时会查 | MVP |
| ③ 讲道理 | 做完一步、`/duck-why`、`/duck-learn` | 不改做法，只给依据和出处 | 不涉及 | `/duck-why` 把手册和名家的说法摆在一起 | MVP |
| ④ 常驻插话 | 你没敲命令、照常干活时 | 核心规则里放几条最要紧的标准，一条一行 | 只提醒 | 看到结果表里只有单个数、没有误差棒，正文却写了「优于」，先问一句跑了几个种子 | 第二步（MVP 之后） |

**卡片走哪条路，看它的认同程度：**
- 共识卡：写明适用范围、配了评测以后，可以走①。适用范围管的是用在哪，来源够不够要另看，两件事不能互相顶替。
- 共识卡里没钉进包装文件的：走②的收尾提醒。已经钉进去的，②里不再重复。
- 你们组的卡：走②，每次开头就读。
- 有分歧的卡、只有一两个来源的卡：只走③。讲道理时说清是谁的说法，有分歧的两派都摆出来。

②没有评测兜底，却对每个用户每次都生效，所以给它设了上限：每次至多三张共识卡，只提醒，不定轻重。

### ① 加查项：一个完整的例子

**先看缺口。** 审稿技能（pre-submission-reviewer）里只有一处提到显著性，还是金融和经济论文的领域规则。ML 论文有没有报误差棒、不同随机种子之间波动多大，它都不查。手册全书也没讲统计上的严谨性（附件 E §5）。

**外面的依据，有两条 10-16 核过原文：**
- **NeurIPS 投稿清单第 7 项**：问论文有没有报误差棒、置信区间或显著性检验，至少支撑主要结论的实验要有。同一份清单也写明，答「否」只要给出理由就行，比如「算力太贵，没报误差棒」；答「否」本身不构成拒稿理由。
- **调参手册**：Google 和 Harvard 合写，附件 C #25，CC BY 4.0，可以改编。其中一节专讲「要不要采纳一个改动」：先换不同的随机种子重跑几次，看清波动有多大，再判断改动是不是真的更好。

两条来源还不够「共识」要求的三家。10-15 还核到两篇专讲这件事的论文（Bouthillier 等 2021、Agarwal 等 2021），但只核了论文存在、题目对得上，内容还没按附件 C 的流程过。所以眼下它只走③。过完其中一篇，这张卡够得上共识，再钉进包装文件（§三第 6 步）。适用范围也要写明：只管有实证对比的实验论文，理论论文不查。

**写成卡，钉进包装文件。** 这张卡编号 E05，标题是「差距要大过种子间的波动」。钉进 `/duck-review` 包装文件以后是这个样子（示意）：

```
跑完原审稿技能的全部检查之后，再查一项（卡 E05，只管有实证对比的实验论文）：
- 主结果有没有报多次运行的波动（误差棒、标准差或置信区间）；
  方法之间的差距，有没有大过不同随机种子之间的波动。
- 既没报，也没说明理由：记为 MAJOR。
- 说明了理由（比如算力不够）：只提醒一句，不算问题。
```

**配评测。** 本机的 Claude Code 2.1.301 自带 `claude plugin eval`，它的帮助 10-16、10-17 在本机看过。

```
evals/review-stats/                 一个用例一个文件夹，约 10 个
  meanstd-01/
    prompt.md      第一行写 /duck-review 投稿前帮我审一遍，下面是一篇 CC BY 许可的 arXiv 论文的实验部分节选
    graders/       评分标准：该指出的有没有漏（漏报）；不该指出的有没有报（误报）；轻重判得对不对
  single-run-explained-01/  …
```

约 10 个用例覆盖这几种情况：报了均值和标准差；报了置信区间或显著性检验；单次运行但说明了算力原因；单次运行也没说明；没有实验的理论论文。用例有两种写法，一种是 `case.yaml`，一种是 `prompt.md` 加 `graders/`，这里用后一种。

- **怎么比**：比的是加查项之前和之后。同一套用例，拿掉这条查项跑一遍，加上再跑一遍，看漏报、误报各变了多少。每个用例默认跑 3 次，评分默认由 Haiku 打。
- **先确认真的走进了包装文件**：评测模板默认让 AI 用调技能的工具自己调用，可我们的子命令设了只有你敲才触发。prompt 第一行写 `/duck-review`，能不能像你敲命令一样触发，要在写包装命令时先试（§三第 2 步）。不能的话，评测时换一份去掉这个设置的包装文件副本。不确认这一点，前后对照量到的就是不带插件的模型。
- **「不装插件」那组对照只当参考**：它默认会加，但量的是整个插件带来的分差。不装插件时模型本来也可能查误差棒，所以证明不了 E05 有用。
- **报告只留本地**：账号支持的话，报告默认会发布到 claude.ai，跑的时候加 `--no-publish`。
- **结果不进仓库**：结果写在 `evals/results/`，已经加进 .gitignore。
- **论文的许可**：挑 CC BY 许可的论文，节选可以放进仓库；不是 CC BY 的，只存 arXiv 编号。
- **Codex**：没有自带的评测命令。Codex 官方插件列表里有一个 plugin-eval，能在临时目录里真跑 `codex exec`、比较改动前后的结果（10-17 看了它的 README）。它有没有评分标准、能不能直接拿来用，要试过才知道。先在 Codex 里挑几条手工对一遍，第 6 步再试它。

**合进去，以后还能回馈上游。**
- 分数站得住，你点头，这条就合进去。
- 以后用着好，问过骆老师，可以提 PR 回 Supervisor-Skills。
- 上游采纳以后，我们同步过来，再把包装文件里这段删掉。

### 为什么不直接改原技能的正文

- **上游更新能直接同步。** 原技能和冻结的快照逐字节一致，上游一改，脚本一比就知道改了什么。
- **许可清楚。** 原技能各自保留原来的许可：6 个在文件头标了 CC-BY-4.0，4 个标了 CC-BY-NC-SA-4.0。我们的改动都写在自己的文件里。
- **改坏了好退。** 删掉包装文件里那一段，就回到原样。

### ② 当尺子

每个包装文件在两处读卡：
- **开头**：读你们组的 `.duck/cards/INDEX.md`，挑出和这次任务相关的卡，当作这一次的规矩。写东西的命令（比如 `/duck-write`）照着写，审东西的命令照着查。
- **收尾**：读插件自带的 `cards/INDEX.md`，挑至多三张共识卡对照一遍。这三张要和这次产物相关，没被静音，也没钉进这个包装文件。命中的卡单独列在「卡片提醒」里，标上卡号，不混进问题清单。

读卡这件事写进每个包装文件，不只写在常驻规则里。常驻规则里的事，AI 跑完几百行的原技能以后很容易忘。

### ③ 讲道理、④ 常驻插话

- ③ 具体是什么样，见《名校教程和技能的关系》§一。
- ④ 放到第二步。核心规则里最多放五条标准，每条一行；做实验时撞上了，先问一句。完整的讲解留到 `/duck-learn`。

## 二 项目长什么样

**运行依赖：**
- 用户要装 Claude Code 或 Codex，外加 Node（开场 hook 用，不装依赖）。机器上没有 Node 时，开场 hook 跑不起来。命令照样能用，因为包装文件自己找得到插件根目录（见 §2.1，10-17 实测），只是没有常驻规则。
- 卡片、手册和 10 个技能都是文本文件，不需要别的。
- 开发时多用一个 `claude plugin eval`，Claude Code 自带。

### 2.1 仓库

```
Doctor-Duck/                           本地就是现在的 mentor-plugin，还没推 GitHub。仓库根目录就是插件（10-17 改）
├─ .claude-plugin/plugin.json          Claude Code 的插件清单，插件名 duck
├─ .claude-plugin/marketplace.json     Claude Code 的安装入口，插件来源写 ./
├─ .codex-plugin/plugin.json           Codex 的插件清单
├─ .agents/plugins/marketplace.json    Codex 的安装入口；现在写本地路径，推 GitHub 以后改成仓库地址
├─ hooks/claude-codex-hooks.json       两个宿主共用，只做一件事：开场注入
├─ bin/duck.js                         hook 脚本，Node，单文件，不装依赖
├─ rules/core.md                       常驻规则，约 35 行，开场注入；含原技能名到 /duck-* 的对照表
├─ rules/off.md                        开关是 off 时注入的一段提示
├─ skills/                             你能敲的命令，全是我们写的包装文件
│  ├─ duck/                            /duck 总入口：菜单、on/quiet/off、一句话分派
│  ├─ duck-survey/ … duck-vibe/        10 个，各指向 library/ 里的原技能
│  └─ duck-why/ duck-learn/ duck-notes/ duck-skill/
├─ library/                            10 个原技能，原样复制，不注册成命令
├─ cards/                              经验卡片，外加一个 INDEX.md 目录
├─ handbook/                           手册的 md：zh/ 约 150 KB，en/ 约 160 KB；PDF 和配图不带
├─ evals/                              评测用例（results/ 不进仓库）
├─ scripts/                            开发用：从上游同步 library/ 和 handbook/，检查卡片
├─ LICENSE、LICENSES/                  按目录写许可
└─ README.md
```

- 包装命令只有 10 个，原技能却有 11 个，因为 `/duck-outline` 一条命令对应技术论文和 benchmark 论文两个模板，按你的论文类型挑一个。
- 讨论稿和调研附件都留在仓库外面，不公开。
- hooks 文件不叫 `hooks/hooks.json`，是照 ponytail：Gemini CLI 会自动加载扩展里这个位置的文件，以后加 Gemini 时，它会把这份给另外两个宿主写的 hook 也加载进去。两个宿主的清单里都写明了它的路径。

**AI 怎么找到 `library/` 和 `cards/`。** 插件装好以后，每台机器上的路径都不一样，升级时还会变。办法是开场 hook 每次都把插件根目录的绝对路径告诉 AI，包装文件里一律写成「插件根目录下的 library/…」。10-17 两个宿主都实跑过：hook 都拿到了 `CLAUDE_PLUGIN_ROOT`，Codex 另外还设了 `PLUGIN_ROOT`；hook 的输入里都带着项目路径。

**hook 没跑时的退路。** 有的宿主不跑开场 hook，有的机器上没装 Node。这时 AI 从命令文件自己的位置往上推两级：宿主加载命令时，会告诉 AI 这份文件在哪。10-17 在 Claude Code 里关掉 hook 试过，模型照这个办法找到了插件根目录。

**为什么不用宿主自带的变量。** 包装文件会从三条路被读到：
- 你直接敲 `/duck-review`：Claude Code 加载时会替换正文里的 `${CLAUDE_PLUGIN_ROOT}` 和 `$ARGUMENTS`，frontmatter 里的设置也生效（10-17 核过插件参考文档）。Codex 会不会替换，还没查到。
- 经 `/duck` 分派：总入口是用读文件的办法读包装文件。
- 你改过的副本：`.duck/skills/` 里的副本也是当普通文件读。

后两条路什么都不替换，变量会原样露出来，frontmatter 里的工具权限、模型这些设置也不生效。所以包装文件不用这些变量；frontmatter 只放名字、描述这类登记用的信息，要做的事全写在正文里。原技能里没有用到这些变量（10-17 查过），照读不受影响。

以上 10-17 用总入口在两个宿主上试过；包装命令写好以后，再逐条试一遍。

**原技能会互相点名。** 比如 vibe-research-workflow 里提到了 idea-evaluator。插件里没有这些名字的命令，所以 core.md 里放一张对照表：idea-evaluator 对应 `/duck-idea`，其余以此类推。

### 2.3 一次 `/duck-review` 是怎么走的

1. **开场。** hook 注入三样东西：插件根目录的绝对路径、`rules/core.md`、`.duck/config.md` 里的状态（开关、静音的卡、关掉的命令）。按 Claude Code 的文档，会话恢复或压缩时开场 hook 会重跑，这些不会丢；Codex 会不会重跑，还没查到。
2. **你敲命令。** 比如 `/duck-review 投稿前帮我审一遍`。
3. **包装文件先查两件事。** 这条命令有没有被你关掉；`.duck/skills/` 里有没有你改过的副本，有的话就照副本做。
4. **读你们组的卡**（②开头），挑出和审稿相关的。
5. **照原技能审稿。** 读 `library/pre-submission-reviewer/SKILL.md` 照做，原技能一字未改。
6. **跑钉进来的加查项**（①），比如 E05。
7. **挑共识卡对照**（②收尾）：至多三张，没钉进来的，跳过静音的。
8. **收尾**，回复里有四样：
   - 问题清单，每条标明来源：原技能、加查项，还是你们组的哪张卡；
   - 卡片提醒（如果有）；
   - 一行「为什么」（③）；
   - 决策行。AI 顺手把这一行追加到 `.duck/decisions.md`。

   完整报告存进 `.duck/reports/`。

### 2.7 还能适配哪些 agent（10-17 新增）

你要的是像 ponytail 那样，一套东西适配很多 agent。ponytail 的适配文档列了 30 多个宿主，按宿主能做什么分成三档。照它的分法，Doctor Duck 在每一档能做到的不一样：

| 档 | 宿主能做什么 | Doctor Duck 能做到什么 | 宿主举例（取自 ponytail 的列表） |
|---|---|---|---|
| 一 | 装整个插件，开会话时跑 hook | 全部：常驻规则、开关、命令 | Claude Code、Codex（本机已实跑）；CodeBuddy 直接认 Claude Code 的清单；Copilot CLI、Cursor、Qoder、OpenCode、Kilo 要各写一个适配文件 |
| 二 | 装整个仓库，命令能用，常驻说明是一份固定文件，不跑 hook | 命令能用；常驻规则只能是固定的一份，读不到项目里的开关 | Gemini CLI、Qwen Code、Kimi Code、Goose、Antigravity CLI、Devin、Grok |
| 三 | 只读项目里的说明文件（AGENTS.md 这类） | 只有常驻规则；还要先把 Doctor Duck 放到本机某处，在说明里写上路径 | Cline、Windsurf、Amp、Zed、Junie、Kiro 等 |

照 ponytail 的几条做法：
- **适配文件要薄**：每个宿主只加一个清单，或者一小段适配代码，都指向同一份 `skills/`、`hooks/`、`rules/`。
- **hook 脚本按宿主输出**：Claude Code、Codex、CodeBuddy、Qoder 认同一种 JSON；Copilot、Cursor 要的字段名不一样。现在只写了前一种，加宿主时再补。

我们比 ponytail 多一个约束：命令要读 `library/` 里的原技能，所以宿主得装整个插件。有的装法只拷单个技能文件夹（比如 `cline skill add`），原技能不在旁边，命令就跑不了。

**每加一个宿主，都要在本机实跑一次，才算支持。** 本机现在只装了 Claude Code 和 Codex，别的 agent 要先装上，多半还要登录你的账号。建议的顺序：
1. CodeBuddy：不用写适配文件，装上试一次就行；
2. Cursor：你自己在用；
3. Gemini CLI 和 Qwen Code：一个扩展文件两家都认；
4. Kimi Code。

你们组用得多的是哪几个，就先做哪几个。
