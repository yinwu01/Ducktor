# /duck-why 和 /duck-learn 改成导师式讲解：设计稿（2026-11-02）

文中提交的日期照提交记录里的时间写，没有换算时区。仓库里的提交多数记的是 -0700（11 月起是 -0800），换成北京时间要加 15 或 16 小时，有的会落到后一天。

## 结论和要你定的事

两条命令改成先判断、再选讲法。每次先看这一步是谁定的、值不值得讲、笔记本里以前记过什么、学生在这次会话里说过什么，再决定是先请学生说说自己的考虑或回顾、直接讲清一件事，还是一两句说明。名家文章和经验卡的意思转换成经验，用 Ducktor 自己的话写进讲解；人名、文章名和卡号写进报告和笔记本。对话里去掉固定的六项、五段标题、开场问话和结尾句。`/duck-learn` 的五段留在报告里；`/duck-why` 的报告换成第 4 节写的结构。

要你定的事：

1. 出处放哪。建议：对话里一般不报人名、文章名和卡号；报告写明卡名加卡号、作者、文章名和链接、手册章节（写成「Supervisor-Skills 手册 3.5「写作细节与Checklist」」并带上游链接），以及这条依据的认同程度；笔记本格式照旧，出处照现行写法（名家和文章、卡名加卡号，或「自己的判断」，skills/duck-why/SKILL.md:75）。学生问到时，对话里直接给出处：问某句话出自哪里，直接说作者、文章名和链接；问怎么深入、要读什么，推荐一两篇。学生没问，不推荐。要和这件事分开的是「学生论文里能引的文献」。10-27 的试用是 journey 测试：模型按学生设定扮演研究生，从读 README 开始把插件用一遍（/SSD1/wuyin/agent-hosts/ducktor/journey/KIT.md:3），下文的 P1 到 P7 都是这样的设定，拿来当依据的地方分量有限。P6 的设定是公卫学生，P6 说道理懂了，但计算机系的名家不能在公卫论文里引（/SSD1/wuyin/agent-hosts/ducktor/journey/out/p6-he/REPORT.md:74），随后要的是本行能引的经典文献（:75、:78）。这一类照现有规则 rules/core.md:40 找学生那一行的文献，给全名和出处；这一句现在只在常驻规则里，没开启的项目读不到，要写进两条命令的步骤。
2. 学生怎么参与。分三点：
   - `/duck-why` 讲之前先问。建议：学生自己定过这件事，记录和这次会话里都没有学生的理由，并且学生的回答会改变接下来讲什么时，才先问一句。这和「不出题」的界线：问学生自己的理由、打算和回顾可以，问有标准答案的知识题不行。
   - `/duck-learn` 请学生回顾这一段。现在每次复盘先问同一句「这次哪一步是你自己定的，哪一步最想重来？」，最初的理由是「复盘要本人参与才算数」（docs/design/2026-10-15-导师插件-调研与讨论稿.md:179，依据是一项复盘的元分析和美军 AAR 的做法），学生的回答用来写「下一步」（skills/duck-learn/SKILL.md:42）。10-27 的试用里，走到 /duck-learn 的五位里，P1、P6、P7 回答了这一问，P2 敲命令时就带上了回答，P3 到了轮数上限没有回答（p3-maya/REPORT.md:172）；四份回答里「最想重来」的那件事都用进了复盘（p1-lin/REPORT.md:149、p2-zhou/REPORT.md:137、p6-he/REPORT.md:97、p7-liu/REPORT.md:142 和 :144），P1 说「问题问得好，让我自己先想一下」（p1-lin/REPORT.md:143）。你 11-02 反对的是每次照问同一句（ducktor.md:25）。两种做法：
     - 建议：按记录问。这一段有学生定的事，记录和会话里还没有学生对这一段的回顾时，复盘之前先问一句，问法提到这一段具体定了什么；全是 AI 定的，复盘以后挑一件 AI 定的判断，请学生说说自己会怎么定，学生不答也照常结束。学生的回答都写进「下一步」。风险：多数复盘都属于其中一种情况，问法会变，有没有这一问是固定的。
     - 不再问。复盘只讲，「复盘要本人参与」这一条不再保留，「最想重来」也不再问。
   - 学生在 /duck-why、/duck-learn 里说「直接讲，别先问我」，在 config.md 记一行「讲法（只管 /duck-why、/duck-learn）：直接讲」，换了会话也算数。有这一行时，两条命令都不问学生的考虑和回顾；要学生定下一步做什么的问题（比如要不要现在补 seed）照问，那是研究决定（rules/core.md:22）。
3. `/duck-learn` 回看上一次复盘的「下一步」。建议：这一段的记录涉及上一次的「下一步」时才提，只说做了没有、谁做的、结果怎样，结论写多强由学生定。风险有两个：被读成检查作业（rules/core.md「不做的事」写着不留作业）；连续几段都涉及时，会成为每次复盘都有的一项。`/duck-why` 不回看上一份报告的「下次」。
4. 学生说「下次这类我想自己定」时，在 `.duck/config.md` 新加的「我自己定」一节记一行，以后碰到这一类先问。Ducktor 不每次主动提这件事：学生回答复盘那一问时，说的定法和 AI 的不一样，或者学生自己说想自己定，才提出可以记下来，先给学生看要记的那一行，学生同意再写。这一条要改常驻规则，改完要重新生成文件并跑 loop 等 e2e（见第 5、6 节）。
   - 学生从哪里知道有这个设定。上面第一种情况要靠学生在复盘那一问里说出和 AI 不同的定法，下面几种情况都没有这个机会：第 2 件事选「不再问」，或者学生记了「讲法：直接讲」；这一段有学生定的事，记录或会话里已经有学生对这一段的回顾，两问都不问；学生答的是自己定的那一步，或者答的定法和 AI 的一样。`/duck-why` 也不提。这时只有学生自己开口才会记。现在的做法是每次复盘都说一句「下次想自己定，说一声就行。」（skills/duck-learn/SKILL.md:57），10-15 的设计就有这一句（docs/design/2026-10-15-导师插件-调研与讨论稿.md:274），README.md:90 也写复盘「帮助你逐步收回学术主导权」。建议复盘报告「这次交给 AI 的判断」一段末尾写一句怎么记进「我自己定」，对话里照上面有条件地提；另一种做法是报告里不写这一句，只在对话里有条件地提。两种做法下，README 都照实写这个设定（第 6 节）。
   - 没开启和 off 的项目：开场注入 rules/idle.md，常驻规则不注入（bin/duck.js:107-109，off 和没开启一样），/duck-learn 照常能用（skills/duck-learn/SKILL.md:63「off 和没开启也写」）。这种项目里平时干活照旧不先问，只有敲 /duck-write 这类包装命令时先问（包装命令第 2 步读这一节）。理由：没开启时不主动，是 0a9e668（10-19，「Opt-in: the duck stays quiet unless a project turns it on」）起的设计；off 时平时不先问，从插件第一版起就是这样（51ffc5c，10-17，当时 off 时常驻规则不加载），off 和没开启一样、skills/duck/SKILL.md:56 现在的说法，是 04e18bf（10-28）定的。总入口 /duck 讲没开启和 off 的说法（skills/duck/SKILL.md:46「平时不出声，只有敲命令时才动」、:48、:56「平时不再先问」）和 README 讲没开启和 off 的几句（README.md:166、:196，i18n/README.en.md:148、:171）也是这样。这样定和 /SSD1/wuyin/agent-hosts/ducktor/out/plugin-review-1102/REPORT.md（下称 REPORT.md）:33 改法 1-1 原来的范围一致。所以学生在这种项目里要记这一行时，给他看那一行的同时照实说：平时干活不会先问，敲 /duck-write 这类命令时才先问。要改成没开启和 off 也先问，除了上面几处，README.md:76、i18n/README.en.md:88、INSTALL.md:47 和 i18n/INSTALL.en.md:47、rules/core.md:43（连带重新生成的 AGENTS.md）、docs/how-it-works.md:35 也要改，这一轮不做；你要这样改，告诉我。
   - 不同意的后果：学生说了这句话，只能写进复盘报告；以后干活没有规则读它，AI 不会自动先问。这时 `/duck-learn` 不提可以记下来；学生自己说想自己定时，照实说这句只记在报告里；报告第四段那句「下次想自己定，说一声就行。」删掉。现在的 `/duck-learn` 就是这种情况：它每次说这一句，学生说了以后没有规则接着处理（REPORT.md 第 1 节）。

## 1. 现在的问题

固定的流程：

- `/duck-why` 每次按同样的六项、同样的顺序讲：最值得学的一点、常见做法和有经验的人怎么想、名家一到两位、回到这次、一句加粗原则、「下次」（skills/duck-why/SKILL.md:60-65）。最后照抄同一句「讲「这次怎么做的」那几句，是照文件和对话记录推出来的……」（:67）。改一两句也「格式一样不少」（:55）。
- `/duck-learn` 每次先问同一句「这次哪一步是你自己定的，哪一步最想重来？」并等回答（skills/duck-learn/SKILL.md:42），AI 全程做完时也照问。然后是五段固定的加粗标题（:53-58），第四段末尾照写「下次想自己定，说一声就行。」（:57）。
- e2e 把其中几项写成了检查：`/duck-why` 的结尾句是必过项（tests/e2e/flow.js:296），加粗行加「下次」、点名名家是建议项（:297、:299）；`/duck-learn` 的开场问话是必过项（:383、:526）。

带来的结果：

- 不管这一步大小、谁定的、学生懂多少，讲法都一样。
- 讲解基本是单向的。两条命令的步骤里，除了 `/duck-why` 不知道讲哪一步时问学生一句（skills/duck-why/SKILL.md:45），主动请学生说的只有 `/duck-learn` 开头那一问，还可以跳过。
- 名家单独成一项，写成「某某在某文里说过某某」。10-27 的试用里，P6 在用了名家的那一轮说「道理懂了，原则那句也好记」，问题出在名家来自计算机系，不能在公卫论文里引（p6-he/REPORT.md:74）；P6 读到一份「顶级导师会盯哪里」三条都是「自己的判断」、没有名家的复盘时，说「这次反而更踏实」（:100）。
- 卡号出现在对话里。P6 要回头问「E02 是啥」（p6-he/REPORT.md:75、:78），P3 把回复里反复出现卡号列为问题（p3-maya/REPORT.md:192）。这是 10-27 旧版本的记录，之后规则改成卡号至多放在卡名后面的括号里（skills/duck-why/SKILL.md:62），README 动图也是这样写的（「差距要大过种子间的波动（卡 E05）」）。按新设计，对话里不写卡号，动图要重画。

### 2.1 Claude Code 的 Learning 输出风格（Anthropic）

来源：官方文档 https://code.claude.com/docs/en/output-styles （页面元数据的修改时间 2026-10-27），和官方插件仓库 anthropics/claude-plugins-official 里 learning-output-style 插件在会话开始时注入的指令。两处官方资料说法不一致：文档页把 Learning 列为内置风格，插件的 README 说它「unshipped」。先后关系和原因未查明。

文档给的示例输出（文档没有完整的多轮对话）：

> ```text
> ● Learn by Doing
>
> Context: The upload form is in place and calls validateFile() before accepting a file. Size and type checks work for images, but the switch statement has no handling for documents yet.
>
> Your Task: In upload.js, implement the case "document" branch inside validateFile(). Look for TODO(human).
>
> Guidance: Decide on a size limit for documents and whether the file extension has to match the MIME type. Return {valid: boolean, error?: string}.
> ```
>
> Claude then stops and waits. Write your code at the `TODO(human)` comment and tell Claude when you're done. Claude responds with one `Insight` about your code and continues the task.

注入的指令里，决定什么时候不请用户动手的一段：

> Don't request contributions for:
> - Boilerplate or repetitive code
> - Obvious implementations with no meaningful choices
> - Configuration or setup code
> - Simple CRUD operations

讲解的要求：

> Focus on interesting insights specific to the codebase or the code you just wrote, rather than general programming concepts.

能看出的做法：常规部分它自己做；碰到有几种合理做法、还没做的设计决定，才把这个决定留给用户自己写，说清已经做了什么、要用户做什么、要权衡什么，然后停下等。讲解只讲这次的代码，不讲通用概念。什么时候触发按判断，触发以后的格式固定（Insight 块；Context、Your Task、Guidance 三段）。文档写明这种风格比默认风格长，也写明输出风格「doesn't guarantee that something always happens or never happens」。

### 2.2 ChatGPT 的 study mode（OpenAI，2025-07-29）

来源：官方发布页 https://openai.com/index/chatgpt-study-mode/ 。11-02 直接访问返回 403，下面的文字取自 Internet Archive 对同一网址的两份快照（2025-07-31、2026-10-22）。两份的对话文字相同，引号写法不同，下面照 2026-10-22 那一份。存档快照算不算官方原文，你可以定。

### 2.3 Gemini 的 Guided Learning（Google，2025-08-06）

来源：Google 官方博客 https://blog.google/outreach-initiatives/education/guided-learning/ 。样例在页首图片里，下面是看图转录，可能有误差。

> 【用户】Help me with this homework problem. A 10.5kg test rocket is fired vertically from Cape Canaveral. Its fuel gives it a kinetic energy of 1925J by the time the rocket engine burns all of the fuel. What additional height will the rocket rise? Assume that air resistance is negligible.
>
> 【Guided Learning】Of course. Let’s break it down together, step by step.
>
> This problem is a great example of the conservation of energy. The rocket has a certain amount of one form of energy when the fuel burns out, and that energy gets converted into another form as it flies higher and eventually stops rising.
>
> What type of energy does the rocket have because it's moving? And what type of energy will it gain as it goes up?

同一张图的左栏，普通 Gemini 直接给出三步解答和答案 h ≈ 18.707 m。

能看出的做法：先点明这道题背后是哪个道理，不先给答案，再问学生。第二篇博文（2025-09-23）的作者写，一个话题结束时它会小结，并给出几个可以接着深入的方向。

### 第一阶段：/duck-why

**情况一：AI 定的一步，依据只有一两个来源。** 学生敲「/duck-why 写引言这一步，你觉得有什么值得我学习和注意的？」

## 4. 规则怎么改

### 两条命令都守的底线

这些写在两条命令的步骤里，不往常驻规则「每次都照做」里加（TRIAGE.md:56 记过往那一节加条目引起的回归）。前五条现行 `/duck-why` 里就有（第 3、4、5 条现行 `/duck-learn` 没有，对它是新加的），后五条是新加或改写的：

1. 讲这次的具体事：哪一步、哪个文件、哪一行、哪个决定。
2. AI 定的不说成学生定的；记录里没有的直说没有。
3. 决策行里写的理由是 AI 当时自己说的，和事实对不上就直说（skills/duck-why/SKILL.md:63）。
4. 提到数字或改动时，说一句学生去哪核对。
5. 有分歧的事两种做法都讲，说清各自适用的条件，不判输赢（skills/duck-why/SKILL.md:61）。范围是 cards/MENTORS.md「意见不一的地方」里的议题和认同程度为「有分歧」的卡（cards/INDEX.md:3；W02、W05、W06、W07）。和现行 rules/core.md:39 的不同：那一条还要求「讲清是谁说的」，新设计在两条命令的对话里一般不报人名，是谁说的写进报告。
6. 按认同程度说话，让学生听得出一条看法有多稳、在什么前提下成立：共识卡和 MENTORS.md「多家都这么说」里的道理，可以说成通行做法，并带上卡上的适用范围；「有出处」的卡、单篇文章和直接引的手册章节只有一两个来源，讲道理本身，带上适用前提，不说成通行做法（cards/MENTORS.md:8）。规则里不给固定的说法。不报人名以后，靠这一条让学生知道一条看法有多稳。依据的范围照现行两条命令各自的写法：`/duck-why` 只用 MENTORS.md、卡片和手册（skills/duck-why/SKILL.md:62）；`/duck-learn` 现在还允许原技能里的说明和投稿清单这类公开规范（skills/duck-learn/SKILL.md:56），这一处和 211320e、bd612f4 删掉原技能出处的做法不一致，REPORT.md 第 3 节已经列过，这一轮不动。`/duck-learn` 用到这两类时：原技能里的说明只有一个来源，照上面一两个来源的说法；投稿清单是会议的规定，说清是哪个会议的哪一项。报告里分别写原技能名加上游链接、清单名加链接。
7. 往这件事上推的部分，和 Ducktor 自己的判断，要让学生听得出来，报告里列出。这和现行 rules/core.md:36「往这件事上推是你的延伸，要说明」一致。规则里不给固定的说法，示意里用过「我的看法是」「我的建议是」「我看」，按句子选。
8. 手册里有领域限定的句子，学生是那个领域时可以讲，并说明领域；别的领域不讲。比如 handbook/zh/03_Paper_Writing/3.5_写作细节与Checklist.md:10、:23 是数据库领域的数字，10-16 架构稿的处理是在卡片上标明领域（docs/design/2026-10-16-Doctor-Duck-项目架构.md:308）。和插件立场冲突的句子不当经验讲，:141（严禁使用大模型或 AI 生成内容）的处理见第 8 件事。
9. 讲到「AI 当时为什么这样做」时，就在那一句里说明是从记录推出来的；记录里没有理由的，说记录里没写。
10. 用到项目 .duck/cards/ 里的卡时，对话里说明这是你们组的规矩：组卡和插件的卡冲突时以组卡为准（rules/core.md:38），学生要分得清哪句是组里定的。学生问出处、问要读什么时，照第 1 件事在对话里直接给出处；学生没问，不推荐。
